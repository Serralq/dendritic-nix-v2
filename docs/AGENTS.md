# NixOS Configuration — AI Onboarding Summary

## What This Is

A single-host NixOS desktop configuration built with **Dendritic Nix** (`vic/den`, aka "den"), an aspect-oriented framework for NixOS/home-manager that replaces traditional host-centric configs with **feature-first composition**.

- **Host**: `hirakata` (x86_64-linux, Intel laptop)
- **User**: `serralq`
- **Framework**: Dendritic (`den`) on flake-parts + home-manager
- **Secrets**: sops-nix with age encryption
- **Dev shell**: devenv (nixfmt, nix LSP)

## Architecture: Dendritic (Aspect-Oriented) Nix

Traditional NixOS configs organize by host → modules. This project organizes by **feature (aspect)** → hosts include features they need.

### Core Concepts

| Concept | What it does | In this project |
|---|---|---|
| **Aspect** | A cross-cutting feature that can target multiple Nix classes (nixos, homeManager, etc.) | `den.aspects.browser`, `den.aspects.desktop-environment` |
| **Context** | Named pipeline stage carrying data like `{host}`, `{host, user}` | `den.ctx.host` is the main entry point |
| **Parametric dispatch** | Functions declare needed args; they're auto-skipped if the context doesn't provide them | `({ user, ... }: ...)` only runs in user contexts |
| **Includes** | Aspect dependency graph — aspects include other aspects | `den.aspects.desktop-environment` includes `den.aspects.hyprland` |
| **Provides** | Named sub-aspects scoped to an aspect | `den.provides.hostname`, `den.provides.define-user`, `den.provides.user-shell` |
| **Batteries** | Built-in reusable patterns from den | `den.provides.primary-user`, `den.provides.user-shell "fish"` |
| **Schema** | Declares entities (hosts, users) and global options | `den.hosts.x86_64-linux.hirakata`, `den.schema.aspect` |

### How It Flows

1. `den.ctx.host { host = den.hosts.x86_64-linux.hirakata }` starts the pipeline
2. The host's aspect (`hirakata`) is resolved via `den.ctx.host.provides.host`
3. Context transitions: `host → user → homeManager-user` (via `into.*` functions)
4. Each stage collects aspect fragments; parametric dispatch filters includes by available context
5. `den.lib.aspects.resolve "nixos" aspect` produces a single NixOS module; similarly for `"homeManager"`

### How Function Arguments Control Dispatch

```nix
# Always applied (no context args needed)
{ nixos.services.foo.enable = true; }

# Only when host context is available
{ host, ... }: { nixos.networking.hostName = host.hostName; }

# Only when both host and user contexts exist
{ host, user, ... }: { nixos.users.users.${user.userName}.extraGroups = [ "wheel" ]; }
```

No `mkIf` or `enable` flags needed — the function's argument pattern IS the condition.

## Key Conventions

### Declaring an Aspect

Every module file follows this pattern:

```nix
{ den, ... }:
{
  den.aspects.my-feature =
    { config, ... }:        # parametric args — can be {host, ...}, {user, ...}, etc.
    {
      includes = [
        den.aspects.other-feature   # reference another aspect
        den.provides.some-battery   # use a built-in battery
        (den.provides.user-shell "fish")  # parametric battery
      ];

      nixos = { pkgs, ... }: {
        # NixOS-level config
      };

      homeManager = { pkgs, ... }: {
        # Home Manager-level config
      };
    };
}
```

The `{ config, ... }` pattern after the aspect name is the **parametric dispatch** — change these to match the context you need (`host`, `user`, or both).

### Adding Flake Inputs

Inputs are declared in TWO places, kept in sync:

1. **`flake.nix`** — auto-generated by `flake-file`, do NOT edit manually
2. **`modules/defaults/dendritic.nix`** or the relevant aspect file — declare via `flake-file.inputs = { ... }`

After adding an input to `dendritic.nix` (or any aspect's `flake-file.inputs`), run `nix run .#write-flake` to regenerate `flake.nix`.

**`follows` policy:** Generally avoid `follows` in flake inputs. The exception is **Hyprland plugins** — native `.so` plugins must be built against the exact same Hyprland they're loaded into, so `hy3`, `hyprexpo`, `hypr-dynamic-cursors`, and any future Hyprland plugin inputs must use `follows = "hyprland"` for their `hyprland` input.

For inputs that need to be available as `_module.args`, add them in the overlays aspect:

```nix
# In modules/defaults/overlay.nix, inside den.aspects.overlays:
nixos = { pkgs, ... }: {
  _module.args.inputs = inputs;
  imports = [ inputs.some-module.nixosModules.default ];
};
```

### Custom Schema Options

Global options are added via `den.schema`:

```nix
# In modules/defaults/overlay.nix:
den.schema.aspect = { lib, ... }: {
  options.minimal = lib.mkOption {
    type = lib.types.bool;
    default = false;
  };
};
```

Then referenced in aspects: `if config.minimal then ... else ...` (see `browser.nix`).

### User/Host Declaration

In `overlay.nix`:

```nix
den.hosts.x86_64-linux.hirakata.users.serralq = { };
```

This declares the host `hirakata` on `x86_64-linux` with user `serralq`. The user's aspect is defined in `modules/hosts/hirakata/serralq.nix`.

### nixpkgs Overlays

Defined in `modules/defaults/overlay.nix` under `den.aspects.overlays`. Uses:

- **`pkgs-stable`** / **`pkgs-heavy`** — separate nixpkgs instances for stable packages and heavy builds (JetBrains IDEs)
- **`inputs.*`** — overlay for pinned packages from flakes (hyprland, tagstudio)
- **`home-manager`** config — shared modules, global pkgs

### Secrets (sops-nix)

- Encrypted at `secrets/secrets.yaml`, age key at `~/.config/sops/age/keys.txt`
- Declared in `modules/defaults/sops.nix` as a `den.aspects.security` aspect
- References in NixOS config: `config.sops.secrets.<name>.path`

## Common Workflows

### Add a new package to an existing aspect

Edit the relevant aspect file (e.g., `modules/singletons/browser.nix`), add the package to `home.packages` or system-level config.

### Add a new singleton aspect

1. Create `modules/singletons/my-feature.nix`
2. Follow the aspect pattern (see "Declaring an Aspect" above)
3. Include it in the user aspect: edit `modules/hosts/hirakata/serralq.nix`, add `den.aspects.my-feature` to `includes`

### Add a new branch aspect

1. Create `modules/branches/my-branch.nix` with sub-features as includes
2. Optionally create a directory `modules/branches/my-branch/` for leaf aspects
3. Include the branch in the user aspect

### Add a new flake input

1. Add `flake-file.inputs.my-input.url = "github:...";` in the relevant aspect file or `modules/defaults/dendritic.nix`
2. If it's a system-level input, also add the URL to the `inputs` block in `modules/defaults/overlay.nix`
3. Run `nix run .#write-flake` to regenerate `flake.nix`

### Add a new host

1. Create `modules/hosts/myhost.nix` with hardware config
2. Create `modules/hosts/myhost/myuser.nix` with user aspect
3. Declare in `modules/defaults/overlay.nix`: `den.hosts.x86_64-linux.myhost.users.myuser = { };`

### Rebuild system

```bash
sudo nixos-rebuild switch --flake .
```

### Regenerate flake.nix

```bash
nix run .#write-flake
```

## Important Notes

- **Never edit `flake.nix` directly** — it's auto-generated by `flake-file`. Use `nix run .#write-flake` after changing inputs.
- **The `minimal` schema option** — `den.schema.aspect.minimal` (default `false`) can tone down aspects. Currently used in `browser.nix` to install fewer browsers.
- **Parametric batteries** — `den.provides.user-shell "fish"` takes arguments; these produce context-aware aspects.
- **The `user` context variable** — available in user-context aspects; provides `user.userName` (e.g., `"serralq"`).
- **Self-referential overlays** — `overlay.nix` defines `pkgs-stable` and `pkgs-heavy` as separate nixpkgs instances for packages that need stable or slow-to-build versions.
- **Cloudflare tunnels** — domain routing is in `networking.nix` via cloudflared; subdomains map to localhost ports.
- **Hyprland is pinned** to v0.56.1 via a flake input overlay; plugins are also version-locked. (`hyprexpo` comes from the `sandwichfarm/hyprexpo` fork — the official `hyprwm/hyprland-plugins` repo dropped it, along with `hyprtrails`, which has no maintained fork and was removed from the config.)
